# Hashline Parity Report — opencode-hashline vs oh-my-pi reference

Date: 2026-09-23 · Method: graphify cross-corpus graph (1005 nodes / 2039 edges over both codebases) + jcodemunch symbol-level verification + direct source reads of every divergence candidate.

Evidence classes: **DIRECT** = read in source (file:line cited). **INFERRED** = concluded from structure, not line-verified.

---

## Verdict

The hash-anchored editing function is implemented at **functional parity with oh-my-pi for the core editing engine** — parse, hash validation, seen-line enforcement, application, block ops, recovery, noop guarding, prompt, and tool integration all exist and are covered by 774 passing assertions. Three behavioral deltas remain, of which **one is correctness-relevant** (boundary-repair pass 2, bead `2k9`, already in_progress). Everything else is platform-shaped divergence or test-infrastructure, not missing function.

**"Acceptable level" answer: yes for the core function** — with `2k9` landed before npm publish (`10r`).

## The one correctness-relevant gap: boundary repair pass 2 (`2k9`)

OMP `repairReplacementBoundaries` (apply.ts:804-961) runs pass 1 local repairs, then defers the missing-closer repair to pass 2 where each candidate group's delimiter imbalance is weighed against `remainingDelta` — the summed residual of the **whole patch** — so a structural closer deleted by one hunk is only re-kept when the patch as a whole is missing it, never when another hunk already removed the matching opener (docstring: "a closer the range deleted is only kept when the patch as a whole is missing it").

Ours `repairEdits` (src/index.ts:1723-1812) performs every repair in one per-edit pass: boundary echo, duplicate suffix/prefix, one-sided echo, INS.POST landing shift. There is no whole-patch residual computation, so multi-hunk patches that jointly unbalance delimiters are not repaired — and conversely a single-hunk repair can't tell whether another hunk already fixed the imbalance. Single-hunk behavior matches OMP pass 1 exactly; multi-hunk behavior diverges.

Second narrow gap — **block-resolution order**: OMP resolves block spans against the tagged snapshot's text _before_ the 3-way merge so the resolved concrete ranges merge cleanly (patcher.ts:395-410). Ours runs recovery on the raw edit list first, then resolves block edits against the recovered text (executeHashlineEdit:2368-2383). When the merge shifts lines, block anchors can resolve against different content than the tag named.
