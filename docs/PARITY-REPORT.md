# Hashline Parity Report — opencode-hashline vs oh-my-pi reference

Date: 2026-09-23 · Method: graphify cross-corpus graph (1005 nodes / 2039 edges over both codebases) + jcodemunch symbol-level verification + direct source reads of every divergence candidate.

Evidence classes: **DIRECT** = read in source (file:line cited). **INFERRED** = concluded from structure, not line-verified.

---

## Verdict

The hash-anchored editing function is implemented at **functional parity with oh-my-pi for the core editing engine** — parse, hash validation, seen-line enforcement, application, block ops, recovery, noop guarding, prompt, and tool integration all exist and are covered by 792 passing assertions. **Update 2026-09-23 (later session):** both correctness-relevant behavioral deltas have since landed — block-resolution-before-recovery (`jqr`, commit cd9feb1) and boundary-repair pass 2 (`2k9`, commit b791b8d). What remains is scope/infrastructure decisions, not missing function.

**"Acceptable level" answer: yes for the core function** — all correctness-relevant gaps landed. Conflict detection was decided **out of scope as a subsystem** (`8sl`, closed 2026-09-23 — rationale in the bead comment: OpenCode's plugin surface has no read-selector extension point for `conflict://`/`:conflicts`, and resolution is already expressible via plain hashline edits; a detection-only warning follow-up is filed as `a9y`, p3). Remaining before npm publish (`10r`): `a9y` (conflict warning, p3) and test infrastructure (`w55`, p3 — deferred to its own worktree).

## Closed correctness-relevant gaps: boundary repair pass 2 (`2k9`) + block-resolution order (`jqr`)

Both were open at report time; both landed 2026-09-23 (commits b791b8d and cd9feb1).

**Boundary repair pass 2** — OMP `repairReplacementBoundaries` (apply.ts:804-961) runs pass 1 local repairs, then defers the missing-closer repair to pass 2 where each candidate group's delimiter imbalance is weighed against `remainingDelta` — the summed residual of the **whole patch** — so a structural closer deleted by one hunk is only re-kept when the patch as a whole is missing it, never when another hunk already removed the matching opener. Ours now ports this machinery verbatim (`findDroppedSuffixClosers`, `netDeletedPrefixBalance`, `slotPatchDelta`, `prefixCanCoverSuffixClosers`, `countProjectedBelowSuffixTail`, `countPayloadRestatedSuffixHead`) in a swap-native model — each replacement edit is its own group, which also avoids OMP's payload double-count in `computeProjectedPrefixBalance` (OMP keys payload inserts in `insertedLineMaps.before` AND pushes `group.payload`; ours is single-count, strictly stricter, matching the guard's intent). Pass 1 single-hunk behavior is byte-identical to before (all 780 pre-existing assertions unchanged at landing).

**Block-resolution order** — OMP resolves block spans against the tagged snapshot's text _before_ the 3-way merge so the resolved concrete ranges merge cleanly (patcher.ts:395-410). Ours previously ran recovery on the raw edit list first, then resolved block edits against the recovered text — when the merge shifted lines, block anchors could resolve against different content than the tag named (and pure-block patches hard-rejected, since block ops are `applyEdits` no-ops). Fixed by resolving against `snapshot.text` before `tryRecover`; regression Test 60 drives the real tool path with a line-shifting external change.
